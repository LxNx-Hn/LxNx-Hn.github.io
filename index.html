02 · AI 활용 방식

AI를 개발 전 과정에 사용합니다.

설계 검토, 구현, 디버깅, 테스트, 문서화까지 작업 성격에 맞춰 사용합니다. 반복 구현은 AI로 줄이고, 그 시간은 인터페이스·예외 조건·평가처럼 직접 판단해야 하는 부분에 더 씁니다.

  1. 01
    문제 정리

    요구사항과 현재 상태를 정리하고 불확실한 부분을 먼저 나눕니다.

  2. 02
    구조 설계

    입출력, 상태, 인터페이스와 변경 범위를 먼저 잡습니다.

  3. 03
    작업 분해

    함수, 쿼리, 테스트처럼 검토 가능한 크기로 나눕니다.

  4. 04
    구현 보조

    방향이 정해진 구현과 반복 작업은 AI로 빠르게 진행합니다.

  5. 05
    코드 검토

    diff를 읽고 상태 변화, 예외 처리와 side effect를 확인합니다.

  6. 06
    실행 검증

    test, build, API, log, 실제 데이터와 학습 결과로 판단합니다.

효율적으로 쓰는 기준

작업마다 AI에 맡기는 범위를 다르게 잡습니다.

판단이 필요한 작업

아키텍처, 애매한 요구사항, root cause, 데이터·평가 기준, 실험 해석은 제가 먼저 기준을 잡습니다. AI는 빠진 조건을 찾거나 여러 대안을 비교하는 데 사용합니다.

구현 속도를 높일 작업

설계가 끝난 함수, SQL, CRUD, 테스트 초안, 반복 수정과 문서 초안은 적극적으로 맡깁니다. 작은 단위로 나누면 생성된 코드를 읽고 고치는 시간도 짧아집니다.

Context · Model

한 함수 문제라면 관련 코드만, 구조 문제라면 필요한 모듈과 제약까지 전달합니다. 복잡한 설계·원인 분석에는 추론 성능이 높은 모델을, 반복 가능한 작업에는 가벼운 모델을 써 시간과 토큰을 조절합니다.

실제 사용 예시

코드를 만드는 것보다, 어디까지 맡기고 어떻게 확인할지를 정합니다.

AI의 답변 자체를 결과로 보지 않고, 변경된 코드와 테스트·로그·학습 결과가 실제로 맞는지 확인한 뒤 다음 작업으로 넘어갑니다.

Hot's POD

SQL 오류 수정

MariaDB correlated subquery alias 오류에서 재현 조건과 기존 쿼리 구조를 먼저 정리한 뒤 대안을 받았습니다. LEFT JOIN 방식은 기존 결과와 비교하고 실행 결과를 확인한 뒤 반영했습니다.

판단할 시간을 확보하는 데 사용

인터페이스가 정해진 함수, 테스트 초안, 형식 변경 같은 작업은 AI로 먼저 처리합니다. 대신 결과를 그대로 넘기지 않고 diff와 실행 결과를 확인하며, 남은 시간은 예외 조건이나 설계 판단에 씁니다.

04 · WORKING NOTES

개발하면서 반복해서 확인하는 기준

프로젝트마다 방법은 달랐지만, 결과가 이상할 때 무엇부터 볼지, 확인하지 못한 값을 어떻게 남길지, 실험 수치를 어디까지 믿을지는 비슷한 기준으로 판단해왔습니다.

01

결과가 이상하면 입력부터 봅니다.

모델이나 라이브러리를 먼저 바꾸기보다 데이터가 어디서 들어왔고, 중간 단계에서 어떤 값이 달라졌는지 따라갑니다.

02

모르는 값을 아는 것처럼 채우지 않습니다.

경로 데이터처럼 실제 값과 추정값이 섞이는 경우에는 estimated, unavailable처럼 상태를 따로 남기는 편입니다.

03

좋은 수치보다 비교 조건을 먼저 봅니다.

RAG 평가와 강화학습 모두 점수가 좋아졌다는 이유만으로 끝내지 않고, 무엇이 같이 바뀌었는지 다시 확인했습니다.

결과가 좋아 보여도 왜 그렇게 나왔는지 설명할 수 있어야 쓸 수 있다고 봅니다.
