02 · AI 활용 방식

개발 과정에 AI를 적극적으로 사용합니다.

설계 검토부터 구현, 디버깅, 테스트, 문서화까지 단계별로 사용합니다. 다만 전체 작업을 한 번에 맡기기보다 필요한 범위를 먼저 정하고, 결과는 코드와 실행 결과로 다시 확인합니다.

  1. 01
    문제 정리

    요구사항과 현재 상태를 정리하고, 아직 확실하지 않은 부분을 먼저 나눕니다.

  2. 02
    구조 설계

    입출력, 상태, 인터페이스와 변경 범위를 잡고 빠진 조건을 점검합니다.

  3. 03
    작업 분해

    함수, 쿼리, 테스트처럼 검토 가능한 크기로 나눕니다.

  4. 04
    구현 보조

    방향이 정해진 반복 구현과 표준 패턴은 AI로 빠르게 작성합니다.

  5. 05
    코드 검토

    diff를 읽고 변수, 상태 변화, 예외 처리와 side effect를 확인합니다.

  6. 06
    실행 검증

    test, build, API, log, 실제 데이터와 학습 결과로 적용 여부를 판단합니다.

업무 분담

판단이 필요한 일과 구현 속도를 높일 일을 나눠서 씁니다.

제가 먼저 판단하는 부분

아키텍처, 애매한 요구사항, root cause, 데이터와 평가 기준, 실험 결과 해석처럼 답이 하나로 정해져 있지 않은 문제는 먼저 기준을 잡습니다. AI는 빠진 조건을 찾거나 대안을 비교하는 데 사용합니다.

AI로 속도를 높이는 부분

이미 설계된 함수 구현, SQL 수정안, CRUD, 테스트 코드, 반복 작업, 문서 초안처럼 범위가 분명한 일은 적극적으로 맡깁니다. 작은 단위로 요청할수록 검토와 수정도 빨라졌습니다.

컨텍스트 관리

필요한 코드와 조건만 전달합니다.

작은 오류 하나를 고치는데 저장소 전체를 넘기지 않고 관련 함수와 호출 경로만 제공합니다. 반대로 여러 모듈을 함께 봐야 하는 설계 문제라면 필요한 구조와 제약을 충분히 넣습니다. 컨텍스트를 줄이면 응답 속도와 토큰 사용도 줄고, 불필요한 수정 범위도 작아졌습니다.

모델 선택

작업 난이도에 따라 추론 비용을 조절합니다.

구조 설계, 복잡한 상태 변화, 원인이 애매한 오류, 실험 해석은 추론 성능이 높은 모델을 사용합니다. 방향이 정해진 함수 구현, 테스트 보완, 문서 정리처럼 반복 가능한 작업은 더 가벼운 모델을 사용해 시간과 토큰을 줄입니다.

검증

설명보다 실행 결과를 봅니다.

AI가 제안한 원인이 그럴듯해도 바로 믿지 않습니다. 변경 폭을 작게 유지하고 diff를 읽은 뒤, 테스트와 로그, 실제 데이터, 학습 결과가 같은 설명을 지지하는지 확인합니다. 맞지 않으면 전체를 다시 만들기보다 원인이 남은 부분만 좁혀 다시 수정합니다.

실제 사용 예시

프로젝트에서도 같은 방식으로 사용했습니다.

설계 검토, 구현 보조, 디버깅, 테스트와 실험 정리까지 작업 성격에 맞춰 AI를 사용했습니다.

관련 커밋 ↗
일반 개발 흐름

설계 → 구현 → 검토 분리

복잡한 작업은 먼저 구조와 인터페이스를 정한 뒤 작은 구현 단위로 나눕니다. 결과는 다시 읽고 실행하면서 확인하고, 문제가 남으면 전체 코드를 다시 생성하기보다 원인이 남은 함수나 조건만 좁혀 수정합니다.

작업 기준

Test / Log설명보다 실행 결과로 판단

04 · WORKING NOTES

프로젝트가 달라도
반복해서 확인하게 되는 것들이 있었습니다.

정해둔 방법을 모든 프로젝트에 똑같이 적용하지는 않습니다. 다만 결과가 이상할 때 무엇부터 볼지, 확인하지 못한 값을 어떻게 남길지, 실험 수치를 어디까지 믿을지는 비슷한 방식으로 판단해왔습니다.

01

결과가 이상하면 입력부터 봅니다.

모델이나 라이브러리를 먼저 바꾸기보다 데이터가 어디서 들어왔고, 중간 단계에서 어떤 값이 달라졌는지 따라갑니다.

02

모르는 값을 아는 것처럼 채우지 않습니다.

경로 데이터처럼 실제 값과 추정값이 섞이는 경우에는 estimated, unavailable처럼 상태를 따로 남기는 편입니다.

03

좋은 수치보다 비교 조건을 먼저 봅니다.

RAG 평가와 강화학습 모두 점수가 좋아졌다는 이유만으로 끝내지 않고, 무엇이 같이 바뀌었는지 다시 확인했습니다.

결과가 좋아 보여도 왜 그렇게 나왔는지 설명할 수 있어야 쓸 수 있다고 봅니다.
