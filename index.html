05 · AI IN DEVELOPMENT

AI를 개발 전 과정에 사용합니다.

설계 검토, 구현, 디버깅, 테스트, 문서화까지 작업 성격에 맞춰 사용합니다. 반복 구현은 AI로 줄이고, 그 시간은 인터페이스·예외 조건·평가처럼 직접 판단해야 하는 부분에 더 씁니다.

  1. 01
    문제·구조 정리

    요구사항과 현재 상태를 정리하고 입출력, 상태, 인터페이스와 변경 범위를 먼저 잡습니다.

  2. 02
    작업 분해·구현

    함수, 쿼리, 테스트처럼 검토 가능한 크기로 나누고 방향이 정해진 구현은 AI로 빠르게 진행합니다.

  3. 03
    코드 검토

    diff를 읽고 상태 변화, 예외 처리와 side effect를 직접 확인합니다.

  4. 04
    실행 검증

    test, build, API, log, 실제 데이터와 학습 결과로 적용 여부를 판단합니다.

효율적으로 쓰는 기준

작업마다 AI에 맡기는 범위를 다르게 잡습니다.

판단이 필요한 작업

아키텍처, 애매한 요구사항, root cause, 데이터·평가 기준, 실험 해석은 먼저 기준을 잡고 AI로 빠진 조건이나 대안을 비교합니다.

구현 속도를 높일 작업

설계가 끝난 함수, SQL, CRUD, 테스트 초안과 반복 수정은 적극적으로 맡기고, 확보한 시간은 예외 조건과 설계 판단에 씁니다.

Context · Model

한 함수 문제에는 관련 코드만, 구조 문제에는 필요한 모듈과 제약까지 전달합니다. 난이도에 따라 모델과 컨텍스트 크기도 조절합니다.

실제 사용 예시

어디까지 맡기고, 무엇을 직접 확인할지 정합니다.

AI의 설명을 결과로 보지 않고 변경된 코드와 테스트·로그·학습 결과가 실제로 맞는지 확인한 뒤 다음 작업으로 넘어갑니다.

07 · WORKING NOTES

개발하면서 반복해서 확인하는 기준

프로젝트마다 방법은 달랐지만, 결과가 이상할 때 무엇부터 볼지, 확인하지 못한 값을 어떻게 남길지, 실험 수치를 어디까지 믿을지는 비슷한 기준으로 판단해왔습니다.

01

입력과 중간 값을 먼저 봅니다.

모델이나 라이브러리를 바꾸기 전에 데이터가 어디서 들어왔고 어느 단계에서 값이 달라졌는지 확인합니다.

02

확인하지 못한 값은 구분해서 남깁니다.

실제 값과 추정값이 섞이면 estimated, unavailable처럼 상태를 따로 두고 임의의 확정값으로 채우지 않습니다.

03

수치보다 비교 조건을 같이 봅니다.

점수가 좋아져도 무엇이 함께 바뀌었는지 확인하고, 같은 조건에서 비교할 수 있을 때만 결과를 해석합니다.

결과를 재현하고 설명할 수 있는 상태까지 확인합니다.
