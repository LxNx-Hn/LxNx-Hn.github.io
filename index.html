02 · AI IN MY WORK

AI를 쓸 때도 먼저
어디까지 맡길지 범위를 줄입니다.

전체 구현을 한 번에 맡기기보다 입력·출력과 바꿀 범위를 먼저 정합니다. 함수나 오류 단위로 좁혀서 요청하고, 나온 코드는 diff를 읽은 뒤 직접 실행해 결과를 확인합니다.

  1. 01
    범위부터 잡기

    입력·출력, 상태, 바꿀 파일을 먼저 정합니다.

  2. 02
    작게 맡기기

    함수, 쿼리, 테스트처럼 끝이 보이는 단위로 요청합니다.

  3. 03
    변경 코드 읽기

    diff와 side effect를 보고 기존 구조와 맞는지 확인합니다.

  4. 04
    직접 돌려보기

    설명보다 test, log, 실제 결과를 기준으로 판단합니다.

WHERE I USE AI

생각이 필요한 일과, 구현을 맡길 일을 나눕니다.

제가 먼저 판단하는 쪽

  • Architecture와 인터페이스
  • 무엇이 원인인지 아직 애매한 문제
  • 평가 기준과 trade-off
  • 실험 결과 해석
  • 서비스에서 어디까지 책임질지

AI에 맡기기 좋은 쪽

  • 이미 설계된 함수 구현
  • SQL·CRUD·테스트 보완
  • 반복되는 코드 수정
  • 문서 초안과 형식 정리
  • 범위가 명확한 디버깅 보조

어떤 모델을 쓰는지보다, AI가 판단해야 하는 범위를 불필요하게 넓히지 않는 쪽을 더 중요하게 봅니다.

04 · WORKING NOTES

프로젝트가 달라도
반복해서 확인하게 되는 것들이 있었습니다.

정해둔 방법을 모든 프로젝트에 똑같이 적용하지는 않습니다. 다만 결과가 이상할 때 무엇부터 볼지, 확인하지 못한 값을 어떻게 남길지, 실험 수치를 어디까지 믿을지는 비슷한 방식으로 판단해왔습니다.

01

결과가 이상하면 입력부터 봅니다.

모델이나 라이브러리를 먼저 바꾸기보다 데이터가 어디서 들어왔고, 중간 단계에서 어떤 값이 달라졌는지 따라갑니다.

02

모르는 값을 아는 것처럼 채우지 않습니다.

경로 데이터처럼 실제 값과 추정값이 섞이는 경우에는 estimated, unavailable처럼 상태를 따로 남기는 편입니다.

03

좋은 수치보다 비교 조건을 먼저 봅니다.

RAG 평가와 강화학습 모두 점수가 좋아졌다는 이유만으로 끝내지 않고, 무엇이 같이 바뀌었는지 다시 확인했습니다.

결과가 좋아 보여도 왜 그렇게 나왔는지 설명할 수 있어야 쓸 수 있다고 봅니다.
